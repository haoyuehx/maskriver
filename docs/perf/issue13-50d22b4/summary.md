# Issue #13 第一阶段真实 SQLite 性能基线（v2，测量已修正）

**范围**：Runner 工作流（`Scan → Plan → Preview → 签名 Approve → Apply`），**不是**完整 CLI 子进程 E2E。真实 SQLite、真实 Ed25519 审批存储、`checkApproval`/preflight/dryRun 全部生效。
**命令**：见 `environment.json`（`-benchtime=5x`，5 次迭代）。
**计时边界**：fixture 构建在 `b.ResetTimer()` **之前**完成，每次迭代前用 pristine 副本重置 target 且计时**停止**。因此 `ns/op` 只含工作流本身。

## 为什么有 v2：上一版测量无效

上一版把 `benchFixture` 放在了 `b.N` 循环内，`ns/op` 里约 **97%** 是建库开销（每行一次 INSERT、两次全新数据库、fsync 上千次），阶段耗时合计只占 `ns/op` 的 1.7–3.1%。独立复核以 pprof、strace 与算术三重证据判定该指标无效。

v2 修正后**阶段耗时合计占 `ns/op` 的 88–103%**（≈100%，个别超过 100% 是阶段计时与总计时边界重叠的正常抖动），说明现在的 `ns/op` 确实在测工作流。

## 结论

1. **`apply` 是主成本**：占 `ns/op` 的 **49–60%**（128 行 22–27 ms，2048 行 319–383 ms）。
2. **吞吐随规模上升并趋于平台**：128 行 ≈2 760–2 838 rows/s，512 行 ≈3 345–3 489，2048 行 ≈3 432–3 614。
3. **`workers=4` 在所有 12 组里都更慢**（约 2–6%）。这与上一版「差异在噪声内」的说法不同：现在信号稳定同向。但 `Workers` 只影响 `maskBatch`，其占总耗时比例很小，所以数据支持的是「**在本工作流里增加 Worker 不划算**」，**不能**据此断言 Worker Pool 本身有缺陷。
4. 上版「每行 12.7 ms 线性」的结论**作废**，那是建库成本。
