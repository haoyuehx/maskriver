# Issue #13 第一阶段真实 SQLite 性能基线

**范围**：Runner 工作流基准（`Scan → Plan → Preview → 签名 Approve → Apply`），**不是**完整 CLI 子进程 E2E。真实 SQLite、真实 Ed25519 审批存储、全部门禁（approval / preflight / dryRun）生效。
**提交**：见 `environment.json` 的 `commit` · 命令与参数同记录。
**重复**：每配置 3 次（`-benchtime=3x`），下表为 3 次的合并结果；仅报中位数意义上的单值，**不声称 p95**。

## 结论（先说最重要的）

1. **吞吐与 Worker 数量无关**：12 组配置全部落在 **76.8–80.9 rows/s**，`workers=1` 与 `workers=4` 的差异在噪声范围内，且**多数配置下 workers=4 略慢**。并发脱敏计算不是瓶颈。
2. **成本随行数严格线性**：每行约 **12.7 ms**（128 行 ≈1.6 s，512 行 ≈6.5 s，2048 行 ≈26 s，三档每行耗时一致）。这是**每次运行固定开销之外的行级线性成本**，指向 SQL 往返/事务提交，而非脱敏 CPU。
3. **`apply` 阶段占据绝大部分时间**：2048 行时 `apply` 约 **341–399 ms/批**级，而 `scan`/`plan`/`preview`/`approve` 均在数十毫秒内。优化方向应优先看 Apply 的 SQL 与提交策略，而不是 Worker Pool。
4. **不要为了提升数字改并发**：`workers=4` 不带来收益，改 Worker 数量不会改善吞吐。

## 一个真实发现：数据形态的上限

最初把 long 形态设为 48 个 `x` 的本地部分，结果 `Plan` 直接以 `ErrUnsafe` 拒绝——**检测规则不认为那种形状是 email**，因此 `UNKNOWN`。把长度降到 24 才得到 `Sensitive` 证据。这不是基准的缺陷，而是规则边界：**值形状越界会被 fail-closed 拒绝**，基准只能覆盖规则能识别的形状。48 字符那一档**未测量**（UNVERIFIED），不做估计。
