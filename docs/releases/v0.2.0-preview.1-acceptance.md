## 1. Release scope

Supported: M1 SQLite `scan`/`preview`/Ed25519 `approve`/`apply`/`validate`;
M2 `--streaming` with budget and transactional outbox; `init-outbox`,
`init-recovery`, read-only `status`, explicit `--resume`, transactional
checkpoint/receipt/progress, bounded prefix/suffix verification, commit-unknown
reconciliation and idempotent replay.

Not supported: MySQL CLI/Recovery, Windows/macOS streaming or recovery, WAL
recovery, cross-store mapping atomicity, generic distributed exactly-once, real
power-loss durability, production-grade PII accuracy, anonymisation,
collision-free replacement, tamper-proof history, and continuous approval
re-check during a long resume.

- CI on the reviewed candidate and on PR #84's final head: Go ubuntu/windows,
  Ubuntu race, isolated MySQL fixture, benchmark/stress and deterministic
  release package SUCCESS. The check runs are on the PR's final head SHA; the
  final release comment records the exact head SHA reviewed for publication.
- Release-binary smoke (`scripts/release-smoke.py`) against the extracted
  candidate: M1 scan/preview/approve/apply/strict validate; M2 streaming
  baseline; real SIGKILL after an observed committed checkpoint with the process
  asserted alive; read-only `status`; `--resume`; strict validate; A/B
  masked-output equality; second resume byte-identical and
  receipt/progress-identical; source unchanged. **PASS, 5/5 consecutive runs.**
- QA found that a concurrent read-only status could turn a transient
  `SQLITE_BUSY` at commit into `CommitUnknown`. Fixed with a bounded 5 s SQLite
  `busy_timeout`; data safety was never violated and the fix is covered by the
  focused suites and the repeated smoke.
- QA found that a SIGKILL during a write leaves a hot rollback journal, which a
  read-only target open cannot recover. Explicit apply/resume now opens the
  target read-write once to let SQLite recover the journal; `status` reports
  `reason=hot_journal` (exit 3; the same exit code also covers cancellation, so `reason=` disambiguates) instead of failing ambiguously. The committed
  regression (`internal/db/recovery_hotjournal_test.go`) creates a real hot
  journal in a child process and proves the read-only open returns
  `ErrHotJournal` with unchanged database bytes, then `RecoverSQLiteJournal`
  removes the journal. A separate release-binary diagnostic additionally
  observed status exit 3, resume to complete/passed, strict validate and an
  idempotent second resume; that diagnostic is not part of the automated suite.
